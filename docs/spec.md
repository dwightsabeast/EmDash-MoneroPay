# EmDash Monero Payments Plugin — Design Spec

> **Snapshot of the live spec, Oct 1, 2026 (live doc revision 57).** The live doc is the source of truth:
> https://claude.ai/code/artifact/f7e24f86-e0b9-494e-91b9-fc1b21988060

> The three diagrams in the live doc are described in text below.

## Summary

This is a sandboxed EmDash plugin that lets visitors pay for products, or leave tips, in Monero, while the plugin itself holds no wallet keys and never calls out to a wallet. A small bridge process beside a view-only wallet pushes signed payment snapshots into the plugin, so the wallet host needs no inbound ports.

Goals:

- **Easy for the admin, first:** under 15 minutes from the registry click to a confirmed test payment, no required settings, and no routine upkeep. If a feature can't fit that budget, the feature changes, not the budget (see Admin setup and upkeep).
- **Sandboxed:** the install consent dialog shows three public routes, two price-API hosts and `content:read`, nothing broader.
- **One-click install:** from the admin registry. The wallet host pairs with one button and one command, and currency and confirmation speed have defaults.
- **No keys in the plugin:** a database leak exposes no wallet material, and a compromised plugin cannot spend or read the wallet.
- **One engine for tips, products and stores:** checkout (fixed price from a product entry), tip jar (open amount, optionally tied to an entry), and orders from any EmDash store through a generic payment contract that other payment methods can copy (see Commerce readiness).

Scope: I read "a feature to send Monero, like a tip" as visitors tipping the site owner. Sending funds *from* the site is out of scope, because it would need a spend key in a hot wallet (see Tip jar mode).

Status: design plus an interactive [proof of concept](https://claude.ai/artifact/TsWK9bimrjQpnXfrfPe7Te). This revision fixes three gaps the proof of concept found: a reorg after settling went unseen, a bridge outage across expiry turned on-time payments into late ones, and the confirmation target moved when the settings changed. It also sets a hard budget for admin setup and upkeep, and plans for EmDash stores under Commerce readiness. Items I could not confirm in the docs are collected at the end under Open questions.

## Key design decisions

The central decision is to flip the connection direction: the wallet side calls the plugin, and the plugin never calls the wallet. That keeps the plugin's network permission to two fixed hosts instead of the broadest grant the sandbox offers.

| Decision | Why | Cost |
| --- | --- | --- |
| Bridge pushes in; the plugin never calls the wallet | Calling an operator-supplied URL needs `network:request:unrestricted` (any public host, empty `allowedHosts`), and that mode still blocks LAN addresses. Pushing in needs only `network:request` with two fixed price-API hosts. | A bridge process to run |
| No keys in the plugin; view-only wallet on the bridge side | KV values are not encrypted, so anything the plugin stores is readable from a database leak. | Refunds are manual |
| Ed25519 public key instead of a shared secret | The plugin stores only a public key. Nothing sensitive sits at rest, and it does not depend on `EMDASH_ENCRYPTION_KEY`. | Needs WebCrypto Ed25519 in the isolate (unverified) |
| Pre-created address pool, one subaddress per invoice, never reused | Invoice creation needs no wallet call. A payment maps to exactly one invoice. | The pool must be topped up (the sync response handles it) |
| Snapshots, not deltas | Retries, replays, reorgs and dropped mempool transactions are all handled by overwriting state. | Slightly larger payloads |
| The theme owns the public UI | Sandboxed plugins cannot inject scripts (`page:fragments` is native-only), and raw routes reject HTML, JS and SVG. | One page and one button in the theme |
| Expire on evidence, and judge lateness from wallet and chain data | The plugin can't tell a bridge outage from a missed payment. The wallet's mempool time and the block height can, and they arrive inside the signed body. | Invoices stay open while the bridge is down; a few minutes of grace on late payments |
| Pair the wallet host with a one-time code | No required settings, and rebuilding the wallet host is one button and one command instead of a key to copy by hand. | Pairing requests are a second path through bridge/sync |
| One install command that sets up a native background service | Most EmDash admins don't run Docker. Monero's own wallet program does the wallet work, so the only code this project maintains is a small bridge. Docker as a requirement and a one-maintainer wallet library were both considered and dropped. | An installer per OS, and verifying Monero's downloads |
| A dedicated shop wallet | A view key can't be changed and reveals everything its wallet receives. A shop-only wallet limits a leak to shop income. | One extra step at setup, and moving funds out now and then |
| Wallet host on its own Linux machine | Keeps the shop's payment history off the site's server, and one platform is easier to test and support. A watcher inside the plugin and running on the site's server were both considered and rejected. | Every admin needs one always-on Linux machine; macOS and Windows wait |

What I borrowed from BTCPay's Monero support: a subaddress per invoice watched only while the invoice is live, and push notification from the wallet (`--tx-notify`) instead of pure polling. What I avoided: its Monero plugin shares one wallet across every store on an instance, and its model has the payment server talk to the wallet directly.

## Architecture

**Diagram (as text): payments flow in through one signed route; the plugin never calls the wallet.**

```text
 Buyer browser ──► Theme (EmDash site)                  Wallet host (separate Linux machine)
                   Pay button and /pay page              ┌──────────────────────────────┐
                   shows address, QR and status          │ monerod  (your full node;    │
                        │ checkout, status               │          or a remote node)   │
                        ▼                                │      ▲                       │
   ┌──────────── Sandbox ─────────────┐                  │ monero-wallet-rpc            │
   │ xmr-pay plugin                   │                  │   view-only wallet,          │
   │  Routes: checkout, status, sync  │◄── signed push ──│   localhost, with login      │
   │  Storage: address pool, invoices │   (POST          │      ▲                       │
   │  Holds only a public key         │    bridge/sync)  │ Bridge (xmr-bridge)          │
   │  Cron: expiry and purge          │                  │   signs and pushes,          │
   └──────────────────────────────────┘                  │   refills address pool,      │
                        │ ctx.http.fetch (two fixed hosts)│   holds the signing key      │
                        ▼                                └──────────────────────────────┘
                   Price APIs (api.coingecko.com, api.kraken.com)
```

Zones: the buyer's browser, the EmDash site (theme outside the sandbox, plugin inside it), and the wallet host. Arrows: browser → theme; theme → plugin (`checkout`, `status`); plugin → price APIs; bridge → plugin (signed push, the only inbound route from the wallet side); bridge → wallet-rpc → monerod. Nothing points from the site to the wallet host.

Buyers and the theme only ever talk to the plugin's public routes. The wallet host starts every connection to the site, and the plugin's only way out is to the two price APIs. A view-only wallet and the bridge's signing key are the only sensitive things, and both stay on the wallet host.

## Admin setup and upkeep

Setup is one registry click, one button and one command, and after that nothing needs routine care. This is a requirement, not a nice-to-have: an admin who finds a payment method fiddly to set up or keep running turns it off. Any feature that can't meet the budget below gets redesigned.

**The budget**

| Measure | Target |
| --- | --- |
| Setup time | Under 15 minutes from registry click to a confirmed test payment, for an admin who can paste one command into a terminal on the machine that will run the wallet host |
| Required settings | None. Pairing fills in the bridge key; currency and speed have defaults |
| Values the admin types | Two, once, at the installer's prompt: the shop wallet's primary address and private view key |
| Commands on the wallet host | One: the install command the admin page shows, with the pairing code built in |
| Software to install first | None. No Docker, no Node, no Monero tools; the installer fetches and verifies what it needs |
| Theme edits | Two components (button and pay page); none once a store offers a payment-method hook |
| Routine upkeep | None: nothing to rotate, renew, refill or reconcile by hand |
| Updates | Automatic and verified; site and wallet host update independently, in either order |
| What needs the admin | Only review items and red health checks, each with one recommended action |

**One-time prerequisites**

1. A sandbox runner on the site. On Node: `npm install @emdash-cms/sandbox-workerd workerd`, then `sandboxRunner: "@emdash-cms/sandbox-workerd/sandbox"` in the `emdash()` config. On Cloudflare: the Workers Paid plan and a `LOADER` binding. Without a runner, registry installs fail with `SANDBOX_NOT_AVAILABLE`.
2. Configured storage (registry installs download a bundle) and an admin with `plugins:manage`.
3. A `products` collection with a numeric `price` field in the site's currency, or a store that supports the payment contract (see Commerce readiness). The collection is a convention, as in the x402 guide, so the plugin needs no field-mapping settings.
4. **An always-on Linux machine for the wallet host, separate from the site's server:** a small VPS, a home server or a NAS. It needs no inbound ports. Linux is the only supported platform at launch.
5. **A Monero node for it to use.** Recommended: your own `monerod`, on that machine or your local network, the most private and secure choice. Allowed: a remote node you trust (trade-offs under Bridge service).
6. **A dedicated shop wallet.** Create a new wallet just for the shop in any Monero wallet app and use its address and view key. Never use your main wallet: a view key can't be changed, and it reveals everything its wallet receives (see Where the wallet host runs).

**Diagram (as text): the admin does seven things; the installer and plugin do the rest.** Budget: under 15 minutes from the registry click to a confirmed test payment. Three places: the admin's wallet app (phone or desktop), the EmDash admin page (browser), and a terminal on the wallet host (a separate Linux machine).

| # | Where | Who | Step |
| --- | --- | --- | --- |
| 1 | Wallet app | Admin | **Create a shop wallet.** A new wallet just for the shop; keep its address and view key. |
| 2 | EmDash admin | Admin | **Install from Registry.** Approve 3 public routes, 2 price hosts, `content:read`. |
| 3 | EmDash admin | Admin | **Connect wallet host.** Copy the one install command; pairing code built in, valid for 15 minutes. |
| 4 | Wallet host terminal | Admin | **Paste the command.** On a separate Linux machine, never the site's server. |
| 5 | Wallet host terminal | Admin | **Answer the prompts.** Shop wallet address and view key, typed once; a remote node only if your own monerod doesn't answer. |
| – | Wallet host | Automatic | **Installer does the rest.** Checks the bridge and Monero's wallet program, creates the view-only wallet, installs a background service, pairs with the site. |
| – | EmDash admin | Automatic | **Checklist turns green.** Paired, wallet synced, addresses ready, price feed. |
| 6 | Wallet app | Admin | **Send a test tip.** At least 0.0001 XMR from any wallet. Setup is done when it settles. |
| 7 | EmDash admin / theme | Admin | **Add the theme pieces.** Pay button and `/pay` page, one import each. None needed with a store adapter. |
| ✓ | — | — | **Taking payments.** Upkeep runs on its own. Act only on review items and red health checks. |

The admin works in three places: their own wallet app, the EmDash admin page, and a terminal on the wallet host. Everything tinted happens on its own.

**Install flow**

1. Admin, Registry, search for the plugin, pick a release, review the permissions and press Install. The consent dialog lists public routes exposed to the internet, network requests to the two price-API hosts, and read access to content.
2. Open the plugin's admin page and press **Connect wallet host**. It shows one install command to copy, with the site URL and a one-time pairing code (valid 15 minutes) built in.
3. Paste the command into a terminal on the wallet host, a separate Linux machine. The installer asks for the shop wallet's address and view key at a prompt, so they never land in shell history. It then downloads and verifies Monero's wallet program, creates the view-only wallet with a restore height of today (no full-chain scan), installs itself as a background service under its own user account, pairs with the site and fills the address pool.
4. The admin page's setup checklist turns green item by item: wallet host paired, wallet synced, addresses ready, price feed answering. The last item asks for a small test tip (at least 0.0001 XMR) from any wallet. When it settles, setup is done.
5. Add the button and the `/pay` page to the theme, one component import each (see Theme integration).

**Configuration (the bare minimum)**

| Setting | Type | Default | Notes |
| --- | --- | --- | --- |
| Bridge public key | filled in by pairing | none | Shown read-only. Pasting a key by hand is a fallback for advanced setups. Not a secret. |
| Currency | select | USD | Fiat currency for prices and rate conversion. |
| Confirmation speed | select | Standard | Fast, Standard or Strict. Presets are in Invoice lifecycle. |

Fixed defaults, not settings: invoice window 30 minutes, late-payment watch window 24 hours, buyer contact data purged after 30 days, settled payments watched until 10 confirmations deep. These are my starting values and can change before release.

**Upkeep the admin doesn't have to do**

- **Addresses:** the pool refills itself; the bridge creates subaddresses whenever the site asks.
- **Restarts and outages:** the wallet host reconciles on start, and invoices wait for it instead of expiring, so nothing is lost.
- **Keys:** the site holds only a public key, so there is nothing to rotate. After rebuilding the wallet host, press Connect wallet host again.
- **Price feeds:** the second host takes over if the first fails.
- **Updates:** once a day the bridge checks for new releases of itself and of Monero's wallet program, and installs them only after their signatures check out. It's on by default and can be turned off. Every sync carries a protocol version, and the plugin accepts the current and previous one, so the site and wallet host never need updating together.
- **Health:** the admin page and dashboard widget show one line per check: paired, last sync, wallet height against the expected height, free addresses, price feed, review items, and a run of unpaid expired invoices. A red line names its fix, for example "Wallet host silent for 12 min. On the wallet host, run `xmr-bridge status`."
- **Review queue:** only cases that need a human land there (underpaid, late, reversed, a reorg that didn't recover). Each shows what happened and one recommended action, applied with one click.

## Plugin manifest

The manifest declares two capabilities, two fixed hosts and two storage collections; that declaration is the whole trust contract the operator consents to. Changing any of it needs a new version, and broadening it is a major version.

```jsonc
{
  "$schema": "./node_modules/@emdash-cms/plugin-cli/schemas/emdash-plugin.schema.json",
  "slug": "xmr-pay",
  "publisher": "did:plc:<your-atmosphere-did>",
  "license": "<SPDX id>",
  "author": { "name": "<you>" },
  "security": { "email": "<security contact>" },
  "name": "Monero Payments",
  "description": "Accept Monero for products or tips. No keys in the plugin.",
  "capabilities": ["content:read", "network:request"],
  "allowedHosts": ["api.coingecko.com", "api.kraken.com"],
  "storage": {
    "pool": { "indexes": ["status"], "uniqueIndexes": ["addrIndex"] },
    "invoices": {
      "indexes": ["status", "expiresAt", "subaddress", ["kind", "createdAt"]],
      "uniqueIndexes": ["token"]
    }
  },
  "admin": {
    "pages": [{ "path": "/", "label": "Monero payments" }],
    "widgets": [{ "id": "xmr-status", "title": "Monero payments", "size": "half" }]
  }
}
```

Placeholders (publisher DID, license, contacts) are yours to fill. The price-API hosts are a first choice; their current terms and rate limits still need checking.

**Routes** (declared in `src/plugin.ts`; public ones appear in the consent dialog, and adding one later re-prompts)

| Route | Method | Access | Body | Purpose |
| --- | --- | --- | --- | --- |
| `checkout` | POST | public | JSON | Create an invoice for a product or a tip |
| `status` | GET | public | query string | Invoice status for the pay page |
| `bridge/sync` | POST | public, signed | raw text (`maxBytes` capped) | Bridge heartbeat, pool top-up and payment snapshots |
| `admin` | POST | private (`plugins:manage`) | Block Kit interactions | Settings, invoice table, row actions |

**Hooks:** `plugin:install` seeds defaults and schedules the cron; `cron` runs the sweep (see Invoice lifecycle); `plugin:uninstall` deletes storage only when `deleteData` is true.

**Storage records**

| Collection | Fields |
| --- | --- |
| `pool` | `addrIndex`, `address`, `status` (`free` or `claimed`), `invoiceId?` |
| `invoices` | `id`, `token`, `kind` (`product`, `tip` or `order`), `productRef?`, `contentRef?`, `orderRef?`, `returnUrl?`, `fiat` (amount, currency), `rate`, `expectedAtomic`, `minAtomic?`, `required` (confirmations, locked at checkout), `subaddress`, `addrIndex`, `status`, `reviewReason?` (`late`, `underpaid`, `reorg` or `reversed`), `createdAt`, `expiresAt`, `createdHeight`, `expiresHeight`, `pendingExpiry?`, `reconfirmingSince?`, `seq`, `transfers[]` (txid, amountAtomic, confirmations, height, timestamp, doubleSpendSeen, unlockTime, seenAt, poolTs), `settledAt?`, `buyer?` (email, note, refundAddress) |

Amounts are stored as decimal strings of atomic units and handled as BigInt, never as floats.

## API contracts

Three public routes carry everything; the bridge's one route does pool top-up, payment reporting and heartbeat in a single signed request. Domain errors are returned as JSON with a stable code, because sandboxed routes cannot set arbitrary HTTP statuses.

**`POST checkout`** (buyer's browser, same origin)

```json
// request
{ "kind": "product", "product": "<entry id or slug>", "email": "optional", "refundAddress": "optional" }

// response
{ "token": "<128-bit random>", "address": "<subaddress>",
  "amountAtomic": "123456789012", "amountXmr": "0.123456789012",
  "uri": "monero:<subaddress>?tx_amount=0.123456789012&tx_description=<text>",
  "expiresAt": "2026-10-01T12:30:00Z", "status": "new" }

// domain errors
{ "error": { "code": "PRODUCT_NOT_FOUND | RATE_UNAVAILABLE | NO_ADDRESS_AVAILABLE | TOO_MANY_OPEN" } }
```

The price is read server-side from the product entry. The client sends only an identifier, never an amount. Tips send `"kind": "tip"` with an optional `contentRef`, an optional `amount` (fiat or XMR) and an optional short `note`.

Stores send `"kind": "order"` with `orderRef`, `amountMinor`, `currency` and `returnUrl`. Here the amount comes from the store, so `status` echoes `orderRef`, `amountMinor` and `currency` back, and the store must check them against its own order before marking it paid (see Commerce readiness).

**`GET status?token=<token>`**

```json
{ "status": "confirming", "confirmations": 3, "required": 5,
  "amountAtomic": "123456789012", "receivedAtomic": "123456789012",
  "expiresAt": "2026-10-01T12:30:00Z", "settledAt": null,
  "pendingExpiry": false, "reconfirming": false }
```

The pay page polls this every 5 seconds. Responses stay `private, no-store`. `pendingExpiry` means the window has closed but no sync from after the deadline has arrived yet, so the page says "Checking for your payment" instead of "Expired". `reconfirming` means a settled payment is being mined again after a reorg.

**`POST bridge/sync`** (bridge only)

Declared with `request: { body: "text", headers: ["x-xmr-ts", "x-xmr-sig"], maxBytes }`, so the handler sees the exact raw bytes.

```json
// request body
{ "v": 1, "seq": 1790000000000, "height": 3012345,
  "addresses": [{ "index": 17, "address": "<subaddress>" }],
  "snapshots": [{ "index": 12, "transfers": [
    { "txid": "<hex>", "amount": "123456789012", "confirmations": 3, "height": 3012343,
      "timestamp": 1790000000, "doubleSpendSeen": false, "unlockTime": "0" } ] }] }

// first sync after pairing starts, signed with the new key
{ "v": 1, "seq": 1790000000000, "height": 3012345, "addresses": [], "snapshots": [],
  "pair": { "code": "<one-time code>", "publicKey": "<base64 Ed25519 key>" } }

// response
{ "ok": true, "poolFree": 41, "poolTarget": 50, "watch": [12, 17] }
```

- **Signature:** `x-xmr-sig` is the base64 Ed25519 signature over `x-xmr-ts + "\n" + rawBody`, verified with WebCrypto against the public key in settings.
- **Freshness:** reject if `x-xmr-ts` is more than 300 seconds from the server clock. Check headers and signature before parsing the body.
- **Pairing:** while a pairing code is active, a body may carry `pair` with the code and a new public key, signed with that new key. The plugin checks the code against its stored hash and expiry, verifies the signature with the key in the body, then stores the key and burns the code. This is the only case where the body is parsed before the signature is checked, and only while a code is active and the body is under 4 KiB. A `pair` field with no active code is rejected.
- **Version:** `v` is the bridge protocol version. The plugin accepts the current and the previous version, and shows "wallet host update available" for the older one.
- **Ordering:** `seq` is the bridge's clock in milliseconds, so it stays monotonic without stored state. A snapshot with a `seq` not newer than the stored one for that invoice is ignored.
- **Transfer fields:** the bridge passes four fields through from `get_transfers`: `height` (0 while unmined), `timestamp` (when the wallet first saw an unmined transfer, or the block time once mined), `double_spend_seen` as `doubleSpendSeen`, and `unlock_time` as `unlockTime`. The plugin adds `seenAt` (when it first heard of the txid) and `poolTs` (the first timestamp reported while unmined).
- **Watch list:** the response names the subaddress indexes the bridge should keep reporting: unfinished invoices, expired and review invoices inside the 24-hour late-payment window, and settled invoices until their payment is 10 confirmations deep, so a reorg after settling is still seen.
- **Idempotent:** retrying the same request is safe, because snapshots overwrite.

## Invoice lifecycle and payment logic

An invoice settles only when the summed spendable, confirmed transfers to its subaddress reach the expected amount, within tolerance, at the required confirmation depth. Nothing is fulfilled at zero confirmations.

**Amount math.** One XMR is 10^12 atomic units. The plugin converts the fiat price with integer arithmetic only.

```latex
expectedAtomic = \lceil fiatMinor \times 10^{12} / rateMinor \rceil
```

`fiatMinor` is the price in minor currency units (cents) and `rateMinor` is the price of one XMR in the same units, as an integer. The rate comes from the first price API that answers, falls back to the second, is cached for about a minute, and is locked into the invoice for its 30-minute window. If both fail, checkout returns `RATE_UNAVAILABLE` rather than using a stale price.

**States**

| State | Meaning | Moves on |
| --- | --- | --- |
| `new` | Address assigned, nothing seen | A transfer appears, or expiry once a sync from after the deadline arrives |
| `seen` | A transfer is in the mempool or below the received threshold | Total reaches the threshold |
| `confirming` | Received amount is enough, confirmations are below the requirement | Confirmations reach the requirement |
| `settled` | Enough amount at enough depth; fulfillment runs. Marked re-confirming if a reorg knocks it shallower | Terminal once 10 deep; `review` if the payment is reversed, or not mined again within 5 blocks |
| `expired` | Window ended with nothing usable received | Reopens if a payment made in time turns up; otherwise terminal after the watch window |
| `review` | Needs the admin: late, underpaid, reorg or reversed | Admin action |

**Diagram (as text): a payment settles only at full depth; every odd case ends in admin review.**

```text
            ┌──────────── full payment seen at once ────────────┐
            │                                                    ▼
 [New] ── partial ──► [Seen] ── enough funds ──► [Confirming] ── confirmed ──► [Settled]
   │                     │                                                       │
 nothing paid      underpaid at expiry                                   reorg after settling
   ▼                     │                                                       │
 [Expired] ── paid late, within 24 h ──►  [Needs admin review: late, underpaid, reorg or reversed] ◄──┘
```

Transitions drawn: New→Seen (partial), Seen→Confirming (enough funds), Confirming→Settled (confirmed), New→Confirming (full payment seen at once), New→Expired (nothing paid), Seen→Review (underpaid at expiry), Expired→Review (paid late, within 24 h), Settled→Review (reorg after settling: not re-mined within 5 blocks, or reversed).

The happy path runs along the top. A full payment seen in one go skips straight to Confirming, and every odd case ends in review rather than being settled or dropped silently. Two moves are not drawn: a settled invoice that a reorg knocks shallower stays settled while it re-confirms, and an expired invoice reopens if its payment turns out to have been made in time.

**Rules**

- **Tolerance:** received at or above 99.5% of expected counts as paid (proposed value). Overpayment settles and records the excess.
- **Multiple transfers:** amounts are summed, so a buyer can top up a short payment to the same address.
- **Only spendable money counts:** a transfer with a non-zero `unlockTime`, or flagged `doubleSpendSeen`, is ignored by every rule here. A time lock would let a buyer pay with coins the site can't spend for years, and a double-spend flag means the coins are already being spent elsewhere. The admin page lists these transfers as not counted.
- **Confirmations locked at checkout:** `required` is worked out from the order value and the speed setting when the invoice is created, and stored on it. Changing the setting affects new invoices only. An admin can raise (never lower) `required` on a single open invoice.
- **Expire on evidence:** an invoice moves to `expired` or `review` only after a sync from after `expiresAt` has covered it. If the bridge is silent at the deadline, the invoice stays open with `pendingExpiry` and the pay page says it is checking.
- **On time or late:** after expiry, only payments made in time count. The evidence, best first: the plugin saw the transfer before `expiresAt`; or the wallet's timestamp from when it was first reported unmined is before `expiresAt`; or, if it was first reported already mined, its block height is at most `expiresHeight` (the height at checkout plus 15 blocks plus a 3-block grace). Block timestamps are not used, because miners set them.
- **Late payment:** a payment made after expiry, inside the 24-hour watch window, moves the invoice to `review` with reason `late`. An expired invoice whose payment turns out to have been made in time reopens and settles normally.
- **Underpaid at expiry:** some funds received but below tolerance moves to `review` with reason `underpaid`. Refunds are done by hand in the wallet, using the buyer's optional refund address.
- **Reorg after settling:** settled invoices stay on the watch list until their payment is 10 confirmations deep. If a reorg knocks the payment shallower but it is still in the mempool or the chain, the invoice stays `settled`, is marked re-confirming, and raises no alert. If it has not been mined again within 5 blocks, it moves to `review` with reason `reorg` and an admin alert.
- **Reversed payment:** if a settled invoice's counted payment falls below the threshold (the transaction is gone, for example double-spent in a reorg), it moves to `review` with reason `reversed` and an admin alert right away. Fulfillment is never reversed automatically.
- **Tips:** no expected amount. An invoice settles when received is at least `minAtomic` (a dust floor, proposed at 0.0001 XMR) at the lowest-tier depth.

**Confirmation presets** (starting values, to tune on stagenet and with real use)

| Order value | Fast | Standard | Strict |
| --- | --- | --- | --- |
| Under 100 (site currency) | 1 | 2 | 10 |
| 100 to 1,000 | 3 | 5 | 10 |
| Over 1,000 | 5 | 10 | 10 |

Monero blocks arrive about every two minutes, so Standard on a small order is roughly four minutes, and 10 confirmations is roughly twenty.

**Cron sweep** (one scheduled task, UTC)

- Expire invoices past `expiresAt` that have no usable payment, but only once a sync from after `expiresAt` has covered them. Until then they wait with `pendingExpiry`.
- Move a settled invoice to `review` if a reorg knocked its payment out of the chain and it has not been mined again within 5 blocks.
- End the watch on invoices past their 24-hour window, and on settled invoices once their payment is 10 confirmations deep.
- Purge buyer email, note and refund address 30 days after an invoice is final.
- Flag the bridge as silent in the admin page if there has been no sync for 5 minutes.

Cron granularity on the Node runner is unconfirmed. If it is coarse, expiry can also be evaluated lazily whenever an invoice is read.

## Bridge service

The bridge is the only component outside EmDash: a small stateless process beside a view-only wallet that signs and pushes snapshots to the plugin. It makes outbound HTTPS calls only, so the wallet host needs no inbound ports. It is a single-file program written in Go, installed by one command. It downloads Monero's official wallet program (`monero-wallet-rpc`), verifies it, and runs it in the background itself, so the admin never sets up wallet-rpc by hand. The only code this project maintains is the bridge; the wallet work is done by software the Monero project maintains.

**Duties**

1. **First run:** download `monero-wallet-rpc` from getmonero.org, check it against the Monero project's GPG-signed hash list, and start it on localhost with a generated login. Create the view-only wallet with `generate_from_keys` (primary address and private view key, no spend key, restore height of today unless set). Generate an Ed25519 keypair with the private key in a file only the service account can read, and pair with the site using the one-time code.
2. **Sync loop:** every 10 to 15 seconds, and immediately when the wallet reports a transaction, read transfers for the watched subaddress indexes (`get_transfers` with incoming and pool transfers, filtered by `subaddr_indices`), keep each transfer's height, timestamp, double-spend flag and unlock time, and POST a signed snapshot to `bridge/sync`.
3. **Pool top-up:** when the sync response says `poolFree` is below `poolTarget`, create the missing subaddresses (`create_address`, account 0, a label such as `xmr-pay`) and send them in the next sync.
4. **Reconcile on start:** the first sync after a restart sends full snapshots for every watched index, so downtime loses nothing.
5. **Height and version:** report `get_height` so the plugin can show how fresh the data is, and send the protocol version `v` with every sync.
6. **Cross-check on remote nodes:** before reporting a transfer as confirmed, compare the block hash at its height with a second node. A mismatch holds the transfer at 0 confirmations and turns a health check red.
7. **Updates:** once a day, check for new bridge and Monero releases, install them only after the signature checks pass, and restart. Reconcile on start covers the gap.
8. **Supervise:** restart `monero-wallet-rpc` if it exits, and report its state in the health checks.

**Configuration**

| Setting | Set by | Notes |
| --- | --- | --- |
| Site URL | the install command | The bridge posts to `/_emdash/api/plugins/xmr-pay/bridge/sync` |
| Pairing code | the install command | One-time, valid 15 minutes. Discarded after pairing |
| Primary address | installer prompt | The shop wallet's primary address |
| Private view key | installer prompt | Lets the wallet see incoming payments, not spend them. Stored readable only by the service account |
| Monero node | installer prompt | Defaults to a local `monerod` if one answers (recommended); otherwise asks for a remote node you trust |
| Restore height | optional flag | Defaults to today's height; set it lower to find older payments |
| Automatic updates | optional flag | On by default |

The settings live in one config file (`/etc/xmr-bridge/config` on Linux) that the admin never needs to open; `xmr-bridge` subcommands change them.

**Wallet setup**

- The installer creates the view-only wallet from the shop wallet's primary address and private view key. The spend key never touches this machine. The wallet-rpc login and the bridge key are generated on the machine; the admin never handles them.
- `monero-wallet-rpc` runs as a child of the bridge, bound to localhost, and its `--tx-notify` is wired to the bridge.
- **Own node recommended, remote node allowed:** your own `monerod` is the most private and secure choice, and the installer uses it automatically when it answers. A remote node works too, with trade-offs: it sees the wallet host's IP and sync timing, and because the wallet trusts its node's view of the chain, a dishonest node could hide payments or report ones that never happened. The bridge's block-hash cross-check catches the second case, and large orders should still use Strict.

**Where the wallet host runs**

The wallet host must run on its own Linux machine, never on the site's server. Funds would be safe either way, because the spend key is never on any server; the separation is about privacy, as the table shows.

| If an attacker fully controls the site's server, they can | Wallet host on a separate machine | Wallet host on the site's server |
| --- | --- | --- |
| Spend or move funds | No | No |
| See every payment the shop wallet receives, past and future | No | Yes |
| Show their own address on the pay page, so new buyers pay them | Yes | Yes |
| Mark orders as paid | Yes | Yes |

- **Required: a separate machine.** The installer checks for a running EmDash site on the same machine and stops if it finds one. A development flag allows both on one machine on stagenet only, and is refused on mainnet.
- **Every site needs this one machine,** self-hosted or on Cloudflare. A small VPS, a home server or a NAS all work.
- **A dedicated shop wallet still matters.** A view key can't be changed, because it comes from the wallet's seed. If the wallet host itself is ever broken into, a shop-only wallet limits the leak to shop income. The admin moves money out to their main wallet from their own device now and then.
- **Separation doesn't stop the worst case.** Whoever controls the site controls what the pay page shows, as with any payment method. That is limited to payments made while the attacker is in, and a run of unpaid expired invoices shows on the admin page.
- **Considered and rejected:** running the wallet host on the site's server (a site break-in would expose the shop's payment history), and a watcher inside the plugin with no machine at all (the site would hold the view key and depend on public nodes).

**The install command**

The Connect wallet host button shows one command, the same pattern Cloudflare Tunnel uses for its connector: copy, paste, done. A sandboxed plugin can't install software on a server itself, and sites hosted on Cloudflare have no server to install on, so one pasted command is the floor.

```sh
# Linux, the only supported platform at launch
curl -fsSL https://<release host>/install.sh | sh -s -- --site https://example.com --pair <one-time code>
```

1. Check that this machine isn't serving the site, then download the bridge for its CPU and check its signature.
2. Ask for the shop wallet's address and view key at a prompt.
3. Download Monero's wallet program and verify it against the signed hash list.
4. Install a systemd service under a new user account, pair with the site and start.

- **Cautious path:** the same steps by hand: download the bridge, check its signature, then run `xmr-bridge install --site <url> --pair <code>`.
- **Optional packages:** a Docker image and distribution packages can come later for admins who prefer them. None is required.

**Failure behavior**

| Failure | What happens |
| --- | --- |
| Bridge down | Checkout keeps working until the address pool runs out (the pool is the runway). Payments are picked up after it returns. Invoices whose window closes during the outage wait for the next sync instead of expiring, so on-time payments still settle. The admin page shows a silent-bridge banner. |
| Site unreachable | The bridge retries with backoff. Snapshots overwrite, so nothing is lost. |
| Wallet-rpc down | The bridge restarts it and skips the cycle, and the plugin sees a stale `height`. |
| Wallet host rebuilt or key lost | Press Connect wallet host and run the new install command. The old key stops working. No funds are affected. |
| View key leaked | It can't be changed. Create a new shop wallet, run the installer with it, and move the funds. New payments go to the new wallet; past shop payments stay visible to whoever has the old key. |

The bridge is plain glue and can be written in any language. It is deliberately replaceable: anything that signs the same payload can stand in for it.

## Theme integration

The theme needs one button and one page, because a sandboxed plugin can neither inject scripts into public pages nor serve HTML. Everything the buyer sees comes from the theme, and everything it decides comes from the plugin.

**Pieces**

1. **Product button:** "Pay with Monero" posts `{ kind: "product", product }` to the `checkout` route and redirects to `/pay/<token>`.
2. **`/pay/[token]` page:** server-fetches `status`, then shows the amount in XMR and fiat, the address with a copy button, a QR code of the `monero:` URI, a countdown to `expiresAt`, and a confirmation counter. It polls `status` every 5 seconds and swaps to a success state on `settled`.
3. **Gating:** for gated content, the page or route checks `status` server-side and treats only `settled` as paid. A client-side flag is never trusted, in the same spirit as the x402 guide's warning that a header's presence must not unlock content.
4. **Tip button:** an entry template renders "Tip in Monero" and posts `{ kind: "tip", contentRef }`, then uses the same `/pay` page.

**Privacy details for `/pay`** (the token sits in the URL)

- Set `noindex` and a no-referrer policy on the page, and load no third-party assets, so the token does not leak through `Referer` or logs elsewhere.
- Render the QR code locally (server-side or from a bundled script), never through a QR web service.
- Send `Cache-Control: private, no-store`.

**Distribution:** the button and the pay page ship as an npm package of Astro components, one import each, and the registry listing's `installation` section carries the two-line snippet. A starter theme can include them later. With a store adapter (see Commerce readiness), no theme edits are needed at all.

**Later:** paid file downloads served by the plugin itself, using `media:bytes:read` and a raw download response. Raw responses buffer up to 8 MiB, so larger files would stay outside the plugin. This adds a capability, so it ships as a later version with a fresh consent prompt.

## Tip jar mode

Tipping is the same engine with an open amount, so it costs one extra field and one extra button, and the plugin still never sends funds. I assumed tips flow from visitors to the site owner; the other readings are listed below.

**Three ways to take tips, simplest first**

| Option | What it is | Gives you | Costs you |
| --- | --- | --- | --- |
| Static address | One primary address and QR in the theme, no plugin | Works today, zero moving parts | Address reuse, no confirmation, no per-post attribution |
| Tip invoices (this plugin) | A fresh subaddress per tip, optional amount, optional entry reference | Confirmation on the page, attribution to an entry, no address reuse | The bridge and the pool |
| Per-author tipping | Each author gets their own wallet or address | Tips routed to people | Per-author wallets and bridges; not in v1 |

**How tip invoices differ from checkout**

- **Amount:** the visitor picks a suggested fiat amount (converted at the locked rate), types an XMR amount, or leaves it open. An open tip settles on any amount at or above the dust floor.
- **Attribution:** an optional `contentRef` (collection and entry id) ties the tip to a post. The admin page can total tips per entry.
- **Message:** an optional short note, plain text only, length-limited, shown to the owner in the admin page and purged with the other buyer data after 30 days.
- **Public display:** off by default. The owner may enable a tips-received count, but never amounts or notes.
- **Confirmations:** the lowest tier of the chosen speed preset, since a tip has nothing to fulfill.

**Why the plugin never sends Monero**

Sending needs a spend key in a hot wallet. Putting one in the plugin, or on the site's host, undoes the property the whole design rests on: a compromise cannot touch funds. Refunds and payouts stay manual in a wallet you control. The admin page can help by listing refund addresses that buyers chose to supply at checkout.

**Other readings of "send Monero"**

- **Owner pays someone from the admin:** same objection. A safer shape is an admin page that builds a transaction request for an offline or hardware wallet to sign, which is a separate project.
- **Visitor-to-visitor tips or author payouts:** a different trust model, since a third party would be holding funds. Not covered here.

## Commerce readiness

xmr-pay should work as a payment method for whatever store EmDash ends up with, and its contract should be generic enough that other payment methods can copy it. Nothing official exists to plug into yet, so the plan covers three outcomes: Cloudflare ships a store, a third-party store becomes the default, or no store appears at all.

**Where things stand (as of Sep 30, 2026)**

- Official templates are Blog, Marketing, Portfolio, Starter and Blank, and the EmDash 1.0 roadmap has no commerce items.
- The only official payment feature is x402: per-request payment for access to content, in stablecoins, settled through a facilitator. It has no carts, orders or checkout.
- The maintainers' guidance for commerce is a native plugin, or a sandboxed plugin for the data and admin side plus theme components for the storefront. That second option is xmr-pay's shape.
- Third-party stores exist: DashCommerce (MIT, Stripe, with a starter storefront) and Ritely eCommerce (native, Stripe on the free tier, more providers on a paid tier). Neither has a way to plug in another payment method.

**The payment contract (the pattern for others)**

Two calls and five statuses, with nothing Monero-specific in them, so a card, Lightning or bank-transfer method could implement the same contract. xmr-pay serves it from its existing routes (`checkout` with `kind: "order"`, and `status`), so the consent dialog doesn't change.

```json
// create a payment for an order the store has already priced
POST payment { "orderRef": "ord_123", "amountMinor": 4999, "currency": "USD",
               "description": "Order 123", "returnUrl": "https://example.com/orders/123" }
-> { "paymentId": "<token>", "payUrl": "/pay/<token>", "expiresAt": "2026-10-01T12:30:00Z" }

// check it on the server before marking the order paid
GET payment?id=<token>
-> { "status": "paid", "orderRef": "ord_123", "amountMinor": 4999, "currency": "USD",
     "paidAt": "2026-10-01T12:14:00Z" }
```

| Contract status | xmr-pay states | What the store does |
| --- | --- | --- |
| `open` | `new`, `seen` | Keeps the order pending |
| `processing` | `confirming` | Shows "payment received, confirming" |
| `paid` | `settled` | Marks the order paid |
| `expired` | `expired` | Releases the order or offers a retry |
| `needs_review` | `review` | Leaves it to the admin |

- **No shared secret between store and payment method.** The store trusts only what it checks: before marking an order paid, it calls `GET payment` on its server and confirms `orderRef`, `amountMinor` and `currency` match its own order. A forged or underpriced payment can't mark anything paid, and the admin has no key to copy between plugins.
- **No webhooks.** The store confirms by checking status on its server when the buyer returns, and can poll open orders. That keeps the plugin's network access at the two price hosts. If a store insists on webhooks, the site's own host would have to join `allowedHosts`, which means a new consent prompt and a major version.
- **Storefront pieces as components.** The button and the `/pay` page are Astro components, so any theme can use them, including an official store theme.
- **Same budget for the admin.** With a store adapter, the admin installs xmr-pay, pairs the wallet host and sees Monero in the store's payment methods. The `products` convention and the theme edits drop away.

**Getting other stores to adopt it**

1. Build the DashCommerce adapter first. It is open source and has a starter storefront, so it is the cheapest real test of the contract.
2. Propose a payment-method interface upstream, first to DashCommerce and then in EmDash's GitHub Discussions. Model it on how EmDash already handles email: one plugin provides `email:deliver`, and other plugins get `ctx.email.send()` once a provider exists. A create and a get call with the five statuses above would let any store list any payment method with no theme edits.
3. Publish the contract as its own short doc with a test suite built from the proof of concept's scenarios, so other payment methods can check their implementation against it.
4. If Cloudflare ships an official store, map the contract onto whatever provider shape it defines. With the engine separate from where prices come from, that should be a thin adapter.

**x402, research only.** If an official store builds on x402, fitting Monero in is harder: today's x402 setup targets EVM chains and Solana through a facilitator. Monero can prove a payment to an address without the view key (`check_tx_key`, `check_tx_proof`), so a Monero x402 scheme is conceivable, but it would need its own facilitator. Tips and product payments stay independent of x402.

**Signals to watch:** releases on `emdash-cms/emdash` and `emdash-cms/templates`, the EmDash 1.0 roadmap issue, GitHub Discussions, and the Cloudflare blog.

## Security model

The worst case for every component is bounded by what it holds: the plugin holds no keys, the bridge holds a view-only wallet and a signing key, and the spend key lives nowhere on the live path. A full compromise of the plugin or the signing key can mark orders paid; it cannot move funds.

| Threat | Mitigation |
| --- | --- |
| Malicious or compromised plugin update | No wallet access to abuse. Network limited to two declared hosts. Any new capability or route needs re-consent. Releases are immutable, publisher-pinned, and can carry build provenance. |
| Database leak | Only the bridge's public key is stored. Invoice tokens (random 128-bit, short-lived) and buyer contact data are exposed, and contact data is purged after 30 days. |
| Forged payment events (signing key stolen) | Every sync is Ed25519-signed. The result is free goods, not lost funds. The admin page lists txids for cross-checking in the wallet. A hold-for-review threshold above a set order value is a candidate later feature. |
| Replay of an old sync | A 300-second timestamp window and a monotonic `seq` per snapshot. Older snapshots are ignored. |
| Address-pool exhaustion by spam checkouts | Cap on open invoices, short invoice window, hashed per-IP buckets with short retention (from `requestMeta`), and a pool target the bridge refills. |
| Price manipulation | The client never sends an amount. Price is read from the product entry server-side. The rate comes from two fixed hosts and is locked per invoice. For store orders, the store checks the amount against its own order before marking it paid. |
| Fulfillment before funds are final | Never at zero confirmations. The minimum is the preset for the order's value tier. |
| Injection through buyer fields | All input validated with a schema, stored as plain text, rendered through Block Kit, which escapes it. |
| Token leakage through the pay page | `noindex`, no-referrer, no third-party assets, `no-store` caching. |
| Wallet host exposure | The wallet-rpc binds to localhost with a login. The bridge makes outbound HTTPS calls only. No inbound ports. |
| Time-locked or double-spent payment | Transfers with a non-zero unlock time or a double-spend flag are not counted, so they never move an invoice toward settled. The admin page lists them as not counted. |
| Reorg or double-spend after settlement | Settled invoices stay watched until the payment is 10 confirmations deep. A re-mined payment just re-confirms; a vanished one goes to review with an alert at once. Fulfillment is not reversed automatically. |
| Pairing code stolen or guessed | The code is 128-bit random, shown only to an admin with plugins:manage, stored only as a hash, single-use and valid for 15 minutes. A new pairing replaces the old key and shows on the admin page. |
| Dishonest remote node | It could hide payments or report ones that never happened, because the wallet trusts its node. Use your own node or one you trust; the bridge cross-checks block hashes at payment heights with a second node before reporting confirmations; large orders use Strict. |
| Full break-in on the site's server | Funds stay safe: the spend key is never on any server. While they're in, the attacker can mark orders paid and show their own address on the pay page, as with any payment method. The view key isn't there, because the wallet host runs on a separate machine. |
| Tampered installer or downloads | The install command checks the bridge's signature, and the bridge checks Monero's wallet program against the Monero project's GPG-signed hash list before running it. Updates go through the same checks. Admins who won't paste an install command can do every step by hand. |

**Privacy**

- The site never holds the view key. It stays on the separate wallet host and belongs to a dedicated shop wallet, so even a break-in there can't reveal the admin's other income.
- A fresh subaddress per invoice keeps buyers' payments unlinkable on-chain.
- No IP addresses are stored. Short-lived hashed buckets exist only for rate limiting.
- Monero hides amounts and senders on-chain, but this plugin's own records (invoice amounts, optional emails and notes) are readable by the site operator. The 30-day purge limits that.

**What the sandbox does and does not guarantee**

It enforces capability gating, per-plugin storage, network isolation and the runner's wall-time limit. It does not limit what a plugin does within a granted capability, and on the Node runner only the 30-second wall limit is enforced, not CPU or memory. The operator can also see everything the plugin stores. The design assumes those limits and keeps the plugin's data harmless.

## Build plan and testing

Build it test-first against Monero stagenet, and settle the three unverified platform questions before writing anything else. Each phase ends in something that can be run.

1. **Spike (gate for everything else).** Confirm Ed25519 verification works inside the sandbox isolate, that a non-browser POST reaches `/_emdash/api/plugins/xmr-pay/bridge/sync` through any proxy or access rules in front of the site, and what cron granularity the Node runner gives. If Ed25519 fails, fall back to HMAC with a secret in encrypted `ctx.settings`, if sandboxed plugins can use it.
2. **Plugin core.** Storage collections, `checkout`, `status`, `bridge/sync` with pairing and protocol versions, the invoice state machine and the cron sweep. Test with `createPluginTestHost()` for route logic, storage and capability enforcement, and `createPluginRuntimeTestHost()` for plugin activation, scheduled tasks and routes. Queue price-feed responses with the host's `http.respond`, and send signed raw-body requests through `routes.request`.
3. **Bridge and installer.** The Go bridge; the install command for Linux (systemd) with the same-machine check; verified downloads of Monero's wallet program; the wallet created from keys with a restore height; pairing; signed automatic updates; and the block-hash cross-check for remote nodes. Test against `monerod --stagenet` end to end on a disposable site: checkout, payment, confirmation, settlement, expiry, a late payment, a restart in the middle, a bridge outage across expiry, a reorg that re-mines a settled payment, a reversed payment, and time-locked and double-spend transfers. The proof of concept scripts each of these.
4. **Admin page.** Block Kit: the setup checklist, the health panel with a fix on each red line, a meter for free pool addresses, and an invoice table with row actions (mark settled, expire, copy txid, raise confirmations).
5. **Setup test.** Time a fresh install by someone who hasn't seen the project, from registry click to a settled test tip, on a separate Linux machine, once with a local monerod and once with a remote node. Anything over 15 minutes, or any step they needed help with, is a bug.
6. **Theme kit.** The button and the `/pay` page as Astro components, local QR rendering, and the `installation` snippet for the listing.
7. **Tip mode.** `kind: "tip"`, open amounts, the dust floor, per-entry totals.
8. **Store adapter.** `kind: "order"`, the payment contract, a DashCommerce adapter, the published contract doc with its test suite, and the upstream proposal (see Commerce readiness).
9. **Release.** Log in with an Atmosphere account, pin the `@emdash-cms/plugin-cli` version, and publish with `emdash-plugin publish` or delegated GitHub releases. Versions are immutable, and the registry is marked experimental, so expect its record format to change.
10. **Later versions.** Receipts through `email:send`, plugin-served paid downloads through `media:bytes:read`, more currencies, hold-for-review above a threshold, macOS and Windows wallet hosts. Each capability addition re-prompts consent.

**Testing limits to plan around:** the test hosts do not reproduce Cloudflare CPU, memory or subrequest limits, and they do not render the admin UI. Use a disposable site for those, and the Block Kit playground for layout.

## Open questions and sources

Seventeen items are unconfirmed; the first three decide whether the design works as written and belong in the spike.

1. **Ed25519 in the isolate.** Does WebCrypto Ed25519 verification work in both the workerd runner and the Cloudflare Worker Loader isolate?
2. **Non-browser POSTs.** Does a request with no `Origin` header reach the plugin's public route through whatever sits in front of the site (reverse proxy, tunnel, access rules, bot rules)?
3. **Cron on Node.** What granularity does the Node runner give `ctx.cron.schedule()`, and does it work when called from `plugin:install`?
4. **Settings storage.** The project's docs snapshot says sandboxed settings live in plain KV. Release notes for EmDash 0.39 describe `ctx.settings` with encrypted secret fields for sandboxed plugins too. This design stores only a public key, so it works either way, but check before adding any secret.
5. **Price APIs.** Current terms, rate limits and supported fiat currencies for the two hosts, and whether a different pair is better.
6. **Client IP behind a proxy.** Whether `requestMeta` gives the real client IP on public routes, or the proxy's, which decides whether per-IP buckets help.
7. **Pool claims.** `updateIf` is documented for Cloudflare and workerd. Confirm the claim loop behaves on the Node runner, and plan retries for PostgreSQL serialization failures.
8. **Field mapping.** Whether the `products` and `price` convention is enough, or a setting for the collection and field name is needed.
9. **Proposed values to tune.** The 99.5% tolerance, 30-minute window, 24-hour watch window, 30-day purge, dust floor, confirmation presets, the 10-block final depth for settled invoices, the 5-block re-mine allowance after a reorg and the 3-block expiry grace.
10. **Registry maturity.** Publishing records are marked experimental and may change. Pin the CLI version.
11. **Time-lock field.** wallet-rpc's reference describes `unlock_time` as the number of blocks until a transfer is spendable, and also returns a `locked` flag. Confirm on stagenet which one reliably marks a buyer-set time lock before relying on it.

Added with the admin-simplicity, commerce and installer work:

12. **Remote node checks.** How reliably the block-hash cross-check catches a dishonest node, and which second nodes to use by default.
13. **Late full payments.** Whether a full payment that arrives late, inside the watch window, should settle on its own instead of going to review. It saves the admin a click; the cost is any price movement since the rate was locked.
14. **Upstream interest.** Whether DashCommerce and the EmDash team want a payment-method interface, and in what shape.
15. **Install command trust.** Whether admins accept a pasted install command, or whether a `.deb` package needs to be the main path.
16. **Automatic updates.** On by default is easiest, but a bad release would reach every install. Consider a short delay before installing, and pinning the release signing key in the bridge.
17. **Same-machine check.** How reliably the installer can tell it's on the site's machine, for example when the site sits behind a tunnel or a reverse proxy.
