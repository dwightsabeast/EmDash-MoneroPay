# Setup friction log

Where setting things up has gone wrong, what fixed it, and what it teaches. It serves two purposes:

1. Fix the doc that caused each snag, so the next person doesn't hit it.
2. Carry the lessons into Coffer's own admin setup. The plugin promises setup in under 15 minutes with nobody's help, so every snag here is a preview of one an EmDash admin could hit. Phase 05 reads this before writing the setup test, and phase 09 before writing the install docs.

Add a row whenever a setup step trips Wyatt or Claude. Newest at the bottom.

## Lessons for Coffer's admin setup

| Lesson | Where it applies |
| --- | --- |
| **Say which machine and which user before every command, and show the prompt the reader should see.** Setup spans several places, and a command in the wrong one fails in confusing ways. | The admin page's install block must say "run this on your wallet host, not your site's server". The installer already refuses to run beside the site; it should also explain clearly when it isn't run with `sudo`, and what to do instead. |
| **No pasteable placeholders.** A placeholder that looks like a real value gets pasted as one. | The admin page builds the install command with the real site URL and pairing code. The installer prompts for the address and view key instead of taking them as arguments. Docs never contain `YOUR_…` values that would run without error. |
| **Put a check right after each step,** so a mistake shows up where it was made, not three steps later. | The setup checklist turns green item by item. Each installer stage prints what it verified. |
| **Make error messages name the fix.** | Health checks already do this. Installer errors should too (for example, "This machine is serving your site. Run the installer on your wallet host."). |
| **Recovery should be as easy as setup.** When a step runs in the wrong place, say how to undo it. | `xmr-bridge uninstall`, re-pairing with Connect wallet host, and a short "if something went wrong" section in the install docs. |
| **Keep a check and the action that follows it in separate, labeled blocks,** one command per line. Commands copied together can merge into one line and do something else. | Install docs and the admin page show one command at a time. The installer runs its own checks instead of asking the admin to run them first. |
| **A long chain of dependent hand-typed commands is fragile.** One skipped or reordered step (or one run as the wrong user) breaks the rest, and the errors point somewhere else. | This is the case for Coffer's single install command: the installer runs the sequence itself, in order, as the right user, and stops with a clear message at the first failed check. Keep the admin's typed commands to the one install line. |
| **Say where every address is opened** (which machine's browser, through what), not just the address. | The admin page and install docs link to the admin page and health views by full URL and say "in your browser". |
| **Don't assume `127.0.0.1` is the local address.** `localhost` can resolve to the IPv6 loopback only. | The installer's local-`monerod` detection and every health check try both loopback addresses; wallet-rpc binds explicitly to `127.0.0.1`, so the bridge connects to exactly that. |
| **Don't make people manage background processes.** Keeping a server alive in a terminal multiplexer is a skill, not a step. | The bridge runs as a systemd service the installer sets up; the admin never starts, attaches to or keeps open anything. `xmr-bridge status` is the only thing they ever look at. |
| **Indentation can mislead; check the structure.** A line indented as if it belongs to one block can still sit inside another, and both a reader and a text search will pass it. | Any check the installer or the plugin's health panel runs on a config file parses it (JSON, systemd unit keys) or checks nesting, never a grep or the indentation. Phase 08's adapter docs show the full enclosing block for each config snippet, not a lone line. |
| **Budget memory, and stop what isn't needed.** A small machine fails all at once when several heavy processes overlap, and recovering it takes someone with access to the host. | The wallet host runs `monerod` and `monero-wallet-rpc`, which are memory-hungry. The installer checks free RAM and disk before it starts and says what is needed. With a local `monerod`, it recommends a minimum and suggests a remote node on small machines. The bridge's health report includes memory pressure, so the admin page can warn before the host falls over. |
| **Hand people a file, not a transcript.** Steps that span machines go wrong in the copying, in both directions: commands copied in pieces, and output that can't be pasted back. | The admin's one install command stays one line; the installer writes its own log (`xmr-bridge status` and a log file) that the admin can attach to a support request instead of copying terminal output. |
| **Run the real tool on anything copied from a document.** A config written from the spec or a doc page can be valid in the doc and invalid in the shipping version, and two validators can disagree. | The install docs (phase 09) and the admin page's install block are tested against the released installer and bridge in CI, not only proofread. The installer validates its own config and the site URL before it starts, and says what is wrong in plain words. |
